# 业务员与助理数据互通 — 设计说明

本文档分析「外贸业务员与助理需要数据互通，助理可帮忙处理订单并转化为采购数据、商家每日付款数据」这一需求，并给出可落地的设计要点，便于纳入《需求文档》与《设计文档》并实现。

---

## 一、需求理解

| 要点 | 说明 |
|------|------|
| **数据互通** | 助理能看见并操作其所属业务员名下的订单、报价、采购等数据，而不是只能看「被单独分配的订单」。 |
| **助理帮忙处理订单** | 助理可参与：订单状态维护、找货、生成/维护报价单、标记付款、生成采购单、跟进发货等。 |
| **转化为采购数据** | 已付款订单 → 生成采购单（现有逻辑），助理也可执行「生成采购单」操作。 |
| **商家每日付款数据** | 需要支持按商家、按日汇总「当日确认的付款」或「当日已付款订单金额」，供对账或报表使用。 |

目标：在**数据归属仍归业务员**（业绩、提成、报表）的前提下，**助理能无缝协作**，且系统能区分「谁操作的」和「数据属于谁」。

---

## 二、核心设计要点

### 2.1 助理与业务员的关联关系

当前设计中，订单上有 `business_user_id`、`assistant_user_id`，但「助理能看到哪些业务员的数据」未显式建模。要实现数据互通，需要**明确助理 ↔ 业务员 的归属关系**。

**建议：增加「助理–业务员」关联表**

| 方案 | 说明 |
|------|------|
| **A. 关联表** | 新增表 `user_business_assistant`（或 `sys_user_assistant`）：`business_user_id`、`assistant_user_id`。一个助理可关联多个业务员，一个业务员可有多个助理。 |
| **B. 用户表扩展** | 在 `sys_user` 上为助理增加 `assigned_business_user_id`（单业务员）。仅支持「一助理对一业务员」时可用。 |

**推荐方案 A**：关联表更灵活，便于后续「一助理对多业务员」或「多助理对一业务员」。

- **数据可见范围**：助理登录后，可访问「与其有关联关系的业务员」名下的：商家、订单、报价单、采购单等（即 `business_user_id IN (其关联的业务员ID列表)`）。
- **操作权限**：在上述可见范围内，助理与业务员使用同一套业务操作（订单状态变更、生成报价、生成采购、登记付款等），仅通过**操作人**区分是谁执行的。

### 2.2 数据归属 vs 操作人（谁做的）

- **数据归属**：订单、报价单、采购单、商家等继续以 `business_user_id`（业务员）为主，用于业绩、提成、老板报表。
- **操作人**：关键操作建议记录「谁执行的」，便于审计与责任追溯。

| 表/场景 | 归属字段（不变） | 建议新增/使用字段 |
|---------|------------------|-------------------|
| 订单 order | business_user_id | 可增加 last_operator_id 或沿用 assistant_user_id 表示「当前主要由谁跟进」；关键操作写操作日志。 |
| 报价单 quotation | business_user_id | 可增加 created_by / updated_by 或仅依赖操作日志。 |
| 采购单 purchase_order | business_user_id | 可增加 operator_id（本次操作人），便于统计「助理代生成」的采购单。 |
| 商家 merchant | business_user_id | 归属不变；助理仅查看/在其下操作订单与采购。 |

这样既满足「数据互通、助理可操作」，又满足「业绩和提成仍按业务员统计」。

### 2.3 商家每日付款数据

「商家每日付款数据」可有两种形态，二选一或同时支持：

| 形态 | 说明 | 实现方式 |
|------|------|----------|
| **统计视图/报表** | 按商家、按日汇总「当日变为已付款的订单金额」或「当日确认的付款金额」。 | 基于现有 `order` 表：按 `merchant_id`、付款确认日（或 `updated_at` 日期）汇总 `status=已付款` 的 `total_amount`；或新增「付款确认时间」字段便于按日汇总。 |
| **付款流水表** | 每笔「商家付款」一条记录，便于与线下到账、平台流水对账。 | 新增表如 `merchant_payment`：id, merchant_id, payment_date, amount, currency, source（订单/手工录入）, related_order_ids（JSON 或关联表）, remark, created_by, created_at。助理/业务员在「确认订单已付款」时可选填或自动生成一条付款记录。 |

**建议**：  
- 先做**统计口径**：按商家+日期从订单表汇总「已付款」金额，形成「商家每日付款」报表或接口。  
- 若后续需要更细的对账与流水，再增加 `merchant_payment` 表及录入/导入能力。

## 三、数据流与协作流程（简述）

```
订单（待报价/已报价/…）
  ↓ 业务员 或 助理 操作
订单状态更新（如：已确认、已付款）、报价单发送/确认
  ↓ 已付款
生成采购单（业务员 或 助理 均可触发）
  ↓
采购单 → 采购执行 → 入库 → 发货
  ↓
按商家+日期汇总 → 商家每日付款数据（报表或付款流水）
```

- **数据可见**：助理可见「关联业务员」下的全部上述数据。  
- **操作权**：助理可执行上述各步操作；系统记录操作人，统计与提成仍按 `business_user_id` 归业务员。

## 四、表结构建议（与现有设计衔接）

### 4.1 助理–业务员关联表（新增）

```text
user_business_assistant（或 sys_user_business_assistant）
  - business_user_id   (Guid, FK → sys_user)
  - assistant_user_id (Guid, FK → sys_user)
  - created_at
  - 主键：(business_user_id, assistant_user_id)
```

- 仅当用户角色为「助理」与「业务员」时使用；系统管理员在「用户管理」或「业务员/助理配置」中维护该表。

### 4.2 订单 / 采购单（扩展，可选）

- **order**：已有 `business_user_id`、`assistant_user_id`。若希望明确「最后操作人」，可增加 `last_operator_id`（Guid，FK → sys_user）。  
- **purchase_order**：可增加 `operator_id`（Guid），表示「本次生成/操作人」，便于区分业务员 vs 助理操作。

### 4.3 商家每日付款（二选一或组合）

- **方式 1（仅统计）**：不新增表，在报表/接口中按 `merchant_id` + 日期 + `order.status=已付款` 汇总金额；如需按「付款确认日」统计，建议在 `order` 上增加 `paid_at`（DateTime?）在「标记已付款」时写入。  
- **方式 2（流水表）**：新增 `merchant_payment`（id, merchant_id, payment_date, amount, currency, source, related_order_ids, remark, created_by, created_at），由「确认付款」或手工录入驱动。

## 五、接口与权限建议

### 5.1 数据范围规则（列表/查询）

- **业务员**：仅能看到 `business_user_id = 当前用户` 的订单/报价/采购/商家。  
- **助理**：能看到 `business_user_id IN (当前用户作为助理所关联的业务员ID列表)` 的订单/报价/采购/商家。  
- 实现方式：在现有「按 business_user_id 过滤」的逻辑中，若当前角色为助理，则先查 `user_business_assistant` 得到其关联的 `business_user_id` 列表，再用 `business_user_id IN (...)` 过滤。

### 5.2 操作权限

- 在上述数据范围内，**助理与业务员**对订单、报价单、采购单、发货等具有同等的**业务操作权限**（创建、修改状态、生成采购、登记付款等）。  
- 菜单/按钮权限仍由现有 RBAC 控制（例如「订单管理」「采购管理」等）；不单独区分「仅业务员」与「仅助理」，通过**数据范围**限制助理只能操作其关联业务员的数据。

### 5.3 新增/扩展接口建议

| 接口 | 说明 |
|------|------|
| GET /api/users/me/business-users | 当前用户若为助理，返回其关联的业务员列表（id、name 等），供前端展示或筛选「我为哪位业务员处理」。 |
| GET /api/merchant-payments 或 GET /api/reports/merchant-daily-payment | 按商家、日期范围返回「每日付款」汇总（或付款流水），数据范围同上（业务员本人、助理见其关联业务员）。 |
| POST /api/merchant-payments | 若采用付款流水表，提供手工录入或由「订单批量确认付款」生成一条付款记录。 |

## 六、需求文档与设计文档可补充内容

### 6.1 需求文档可增加（示例）

- **业务员与助理数据互通**：助理可查看并操作其关联业务员名下的订单、报价、采购等；处理结果（采购数据、付款数据）归属仍为该业务员；系统支持按商家、按日汇总「每日付款」数据。  
- **商家每日付款数据**：支持按商家与日期查询/导出「当日付款金额」或付款流水，供对账与报表使用。

### 6.2 设计文档可增加（示例）

- **助理–业务员关联**：通过 `user_business_assistant` 表配置；助理数据范围 = 其关联业务员的数据。  
- **操作人记录**：订单/采购单（及可选付款流水）记录操作人；数据归属仍以 `business_user_id` 为准。  
- **商家每日付款**：统计口径（基于 order + paid_at）或/及 `merchant_payment` 表结构；相关接口与权限。

## 七、实现顺序建议

1. **Phase 1**：实现助理–业务员关联表与维护界面（用户管理或独立配置页）；列表/查询接口中助理按「关联业务员」扩大数据范围。  
2. **Phase 2**：订单/报价/采购等写操作统一允许助理在其数据范围内操作，并在关键节点记录操作人（如 `operator_id` 或操作日志）。  
3. **Phase 3**：订单增加「付款确认时间」或付款流水表，实现「商家每日付款」统计/报表及必要接口。  

按上述顺序可实现「业务员与助理数据互通，助理帮忙处理订单并转化为采购数据与商家每日付款数据」的需求，且与现有权限与数据归属设计一致。
