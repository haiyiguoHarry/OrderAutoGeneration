## 一、系统架构

### 1.1 总体架构

采用 **前后端分离** 的 B/S 架构：

```
┌─────────────────────────────────────────────────────────────────┐
│                        浏览器 (Web 前端)                          │
│   React + 路由 + 状态管理 + 权限控制 + 看板/报表                  │
└─────────────────────────────────────────────────────────────────┘
                                    │ HTTPS
                                    ▼
┌─────────────────────────────────────────────────────────────────┐
│                      网关 / 反向代理 (可选)                        │
│   认证、限流、静态资源、API 路由                                    │
└─────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼
┌─────────────────────────────────────────────────────────────────┐
│                     应用服务层 (Backend API)                       │
│   用户/权限 | 商家/订单 | 报价/采购 | 仓储/发货 | 报表/提成         │
└─────────────────────────────────────────────────────────────────┘
                                    │
          ┌─────────────────────────┼─────────────────────────┐
          ▼                         ▼                         ▼
┌─────────────────┐    ┌─────────────────┐    ┌─────────────────┐
│  关系型数据库     │    │  文件/对象存储   │    │  缓存 (Redis)    │
│  (PostgreSQL)    │    │  报价/导出文件   │    │  会话/权限缓存   │
└─────────────────┘    └─────────────────┘    └─────────────────┘
```

### 1.2 技术栈建议

| 层次       | 技术选型（建议）     | 说明 |
|------------|----------------------|------|
| 前端       | React + Vite + Ant Design / Material UI | SPA，组件化，权限控制 |
| 后端       | ASP.NET 8 (Web API)  | RESTful API，事务、权限、JWT 认证 |
| 数据库     | PostgreSQL           | 业务主库 |
| 缓存       | Redis                | 会话、权限、热点数据 |
| 文件存储   | 本地/OSS             | 报价单、导出 Excel/PDF |
| 部署       | Docker + Nginx       | 便于扩展与运维 |

## 三、权限与角色设计

### 3.1 角色与数据范围

| 角色         | 数据范围           | 可操作范围 |
|--------------|--------------------|------------|
| 系统管理员   | 全部               | 用户/角色/权限/参数/日志，不参与业务数据修改 |
| 老板         | 全部（只读业务）   | 查看全部销量/盈利/提成，审批提成，不可改订单/采购等 |
| 外贸业务员   | 本人负责的商家及下属订单/报价/采购 | 本人商家与订单全流程，可分配任务给助理 |
| 助理         | 被分配的任务与订单 | 找货、采购跟进、发货等，受业务员分配与权限约束 |

### 3.2 权限矩阵（概要）

| 功能/资源        | 系统管理员 | 老板 | 外贸业务员 | 助理 |
|------------------|------------|------|------------|------|
| 用户/角色管理    | ✓          | —    | —          | —    |
| 系统参数/日志    | ✓          | 查看 | —          | —    |
| 销量/盈利报表    | 查看       | ✓    | 本人       | —    |
| 提成规则/计算    | 查看       | ✓ 审批 | 本人查看   | 本人查看 |
| 商家管理         | 查看       | 查看 | 本人 CRUD  | 查看（分配） |
| 订单管理         | 查看       | 查看 | 本人 CRUD  | 分配部分 |
| 报价单           | 查看       | 查看 | 本人 CRUD  | 分配部分 |
| 采购单           | 查看       | 查看 | 本人       | 分配部分 |
| 仓储/发货        | 查看       | 查看 | 本人       | 分配部分 |
| 售后             | 查看       | 查看 | 本人       | 分配部分 |

（具体到菜单、按钮级权限建议在 RBAC 表中配置，见 4.2。）

### 3.3 RBAC 模型

- **用户 (User)**：登录账号，归属部门（可选），绑定一个主角色。
- **角色 (Role)**：系统管理员、老板、外贸业务员、助理等；可扩展自定义角色。
- **权限 (Permission)**：菜单权限 + 接口/按钮权限，如 `order:create`、`report:sales`。
- **用户-角色**：多对多（可选），通常一人一角。
- **角色-权限**：多对多；数据权限（本人/本部门/全部）由角色或规则引擎控制。
- **数据归属**：订单/报价/采购等表带 `business_user_id`（业务员）、`assistant_user_id`（助理可选），查询时按角色过滤。

## 四、数据库设计（核心表）

### 4.1 ER 关系概要

- **用户、角色、权限**：用户 ↔ 角色 ↔ 权限（多对多）。
- **商家**：归属业务员，一对多**店铺**（merchant_shop），一对多订单。
- **商家店铺**：归属商家，一对多**商品**（product），一对多订单；订单需关联到具体店铺。
- **商品**：归属店铺，供找货表、报价、订单行、运费计算、采购引用；扩展重量（克）、包装尺寸、英文名、客户链接等以支撑找货表/报价表。
- **快递公司**：主数据；**快递国家运费**：快递公司 + 目的国家 + 运费/时效，供报价与发货使用。
- **订单**：归属商家、**店铺（可选）**、业务员，关联报价单、采购单、发货记录。
- **报价单**：关联订单行，状态：草稿/已发送/已确认/已拒绝。
- **采购单**：由订单/报价单汇总生成，关联采购明细、入库、发货。
- **提成**：按业务员/助理、时间段、规则计算，支持老板审核与调整。

### 4.2 核心表结构（逻辑）

#### 4.2.1 系统与权限

- **sys_user**：id, username, password_hash, real_name, role_id, dept_id, status, created_at, updated_at
- **sys_role**：id, code, name, data_scope（全部/本部门/本人）, created_at
- **sys_permission**：id, code, name, type（menu/button/api）, parent_id, path, sort
- **sys_role_permission**：role_id, permission_id
- **sys_operation_log**：id, user_id, module, action, target_id, detail, ip, created_at

#### 4.2.2 商家、店铺、商品与订单

- **merchant**：id, name, platform, shop_name（可保留作默认展示）, contact, settlement_type, business_user_id, status, created_at, updated_at
- **merchant_shop**（商家店铺）：id, merchant_id, name（店铺名称）, platform（Shopee 等）, shop_url/shop_identifier, remark, status, created_at, updated_at
- **product**（商品，店铺维度）：id, merchant_shop_id, sku, name, name_en（英文名）, spec, image_url, platform_url, weight_kg, weight_g（克，可选）, length_cm, width_cm, height_cm（包装尺寸）, link_1688, customer_link, factory_link, material, style_name, size_chart, package_note, suggested_purchase_price, suggested_sale_price, remark, status, created_at, updated_at
- **order**：id, merchant_id, **merchant_shop_id（可选，所属店铺）**, order_no, platform_order_id, business_user_id, assistant_user_id, status, total_amount, currency, order_time, paid_at, last_operator_id, created_at, updated_at
- **order_item**：id, order_id, **product_id（可选，关联商品）**, sku, product_name, spec, quantity, price, link_1688, purchase_price, remark

#### 4.2.3 报价与采购

- **quotation**：id, merchant_id, quotation_no, business_user_id, status（草稿/已发送/已确认/已拒绝）, total_amount, valid_until, sent_at, confirmed_at, created_at, updated_at
- **quotation_item**：id, quotation_id, order_id, order_item_id, sku, product_name, spec, quantity, unit_price, amount, 1688_link
- **purchase_order**：id, purchase_no, source_type（order/quotation）, business_user_id, status（草稿/已下发/采购中/部分到货/已到货）, total_quantity, created_at, updated_at
- **purchase_item**：id, purchase_order_id, sku, product_name, spec, quantity, 1688_link, supplier, express_no, received_qty, order_item_ids（关联订单行，可 JSON 或关联表）

#### 4.2.4 快递与物流

- **express_company**（快递公司）：id, code, name, contact, remark, status, created_at, updated_at
- **express_country_rate**（快递国家运费）：id, express_company_id, country_code（如 FR/BE/CH）, country_name, unit_price, lead_days_min, lead_days_max, charge_rule（按重/体积）, remark, effective_from, effective_to, created_at, updated_at

#### 4.2.5 仓储与发货

- **warehouse_receipt**：id, purchase_order_id, receipt_no, received_at, operator_id, status
- **shipment**：id, order_id, shipment_no, express_company, express_no, weight, packed_at, shipped_at, operator_id
- **shipment_item**：id, shipment_id, order_item_id, quantity

#### 4.2.6 经营与提成

- **commission_rule**：id, role_type（业务员/助理）, rule_type（按销售额/按利润/阶梯）, config（JSON）, effective_from, effective_to
- **commission_record**：id, user_id, period_type（月/周）, period_value, sales_amount, cost_amount, profit_amount, commission_amount, status（待审核/已审核）, approved_by, approved_at, remark

（实际建表时需统一主键策略、索引、审计字段；枚举状态建议用字典表或常量。）

## 五、接口设计（概要）

### 5.1 规范

- RESTful：GET 查询、POST 创建、PUT/PATCH 更新、DELETE 删除。
- 统一响应：`{ code, message, data }`；分页：`{ list, total, page, pageSize }`。
- 认证：JWT 或 Session；接口需携带 Token，后端按权限与数据归属过滤。

### 5.2 核心 API 分组

| 分组       | 示例接口 |
|------------|----------|
| 认证       | POST /api/auth/login, POST /api/auth/logout, GET /api/auth/profile |
| 用户/角色  | GET/POST/PUT/DELETE /api/users, /api/roles, /api/roles/{id}/permissions |
| 商家       | GET/POST/PUT/DELETE /api/merchants, GET /api/merchants/{id}/orders |
| 商家店铺   | GET/POST/PUT/DELETE /api/merchants/{id}/shops 或 /api/shops?merchantId=, GET /api/shops/{id} |
| 商品       | GET/POST/PUT/DELETE /api/shops/{id}/products 或 /api/products?shopId=, GET /api/products/{id} |
| 订单       | GET/POST/PUT /api/orders, GET /api/orders/{id}, POST /api/orders/import |
| 报价单     | GET/POST/PUT /api/quotations, POST /api/quotations/{id}/send, POST /api/quotations/{id}/confirm |
| 采购单     | POST /api/purchase-orders/generate-from-orders, GET/PUT /api/purchase-orders |
| 仓储/发货  | POST /api/warehouse/receipts, GET /api/shipments, POST /api/shipments, PUT /api/shipments/{id}/ship |
| 报表       | GET /api/reports/sales, GET /api/reports/profit, GET /api/reports/commission |
| 提成       | GET /api/commission/rules, GET /api/commission/records, PUT /api/commission/records/{id}/approve |
| 快递公司   | GET/POST/PUT/DELETE /api/express-companies, GET /api/express-companies/{id}/rates |
| 国家运费   | GET/POST/PUT/DELETE /api/express-country-rates, GET /api/express-country-rates?companyId=&country= |
| 订单转换   | POST /api/order-conversion/convert（上传报价新+Tracking&Cost 文件），GET 下载生成文件 |

（具体请求/响应字段在开发阶段按前后端约定补充。）

## 六、关键流程设计

### 6.1 报价单生成与确认流程

1. 业务员按商家/日期筛选订单（状态为待报价或已同步）。
2. 系统按订单行汇总 SKU/规格/数量，带出已维护的 1688 链接与建议单价，生成报价单（草稿）。
3. 业务员可编辑单价、备注，确认后“发送”，状态变为已发送，记录发送时间；可选邮件/站内信通知商家。
4. 商家确认后，业务员在系统中将报价单置为“已确认”，订单状态批量更新为“已确认待付款”；若拒绝则置为“已拒绝”，可填原因。

### 6.2 采购表生成与采购执行流程

1. 商家付款后，业务员将对应订单标记为“已付款”。
2. 选择“已付款”订单（或按报价单），执行“生成采购单”：按 SKU/规格/1688 链接汇总数量，生成采购单及明细，状态为草稿。
3. 确认后下发采购单（状态：已下发），分配采购负责人（可来自采购组或助理）。
4. 采购人员在 1688 下单，维护供应商、快递单号；到货后登记入库（入库单关联采购单），更新采购单“已到货”或“部分到货”。
5. 订单状态可随采购单/入库进度更新为“采购中”“到仓待发”等。

### 6.3 发货与面单流程

1. 对状态为“到仓待发”的订单，生成发货单（可一单多包裹），关联订单行与数量。
2. 分拣完成后，调用面单打印接口（或生成 PDF/对接打印机），打印快递面单。
3. 打包后登记快递公司、快递单号、发货时间，订单状态更新为“已发货”，进入物流跟踪与售后模块。

### 6.4 提成计算与审核流程

1. 系统按“提成规则”（按销售额/利润/阶梯等）及业务员/助理数据范围，定期（如每月）自动生成提成记录（待审核）。
2. 老板在“提成管理”中查看每人的销量、利润、计算出的提成金额，可调整金额并填写备注。
3. 确认后“审核通过”，状态变为已审核，可作为发放依据；需留痕（调整前后值、操作人、时间）。

## 七、前端设计要点

### 7.1 页面结构

- **布局**：顶栏（Logo、菜单、用户与退出）+ 侧栏（按权限动态菜单）+ 内容区。
- **路由**：按模块划分（/system, /merchant, /order, /quotation, /purchase, /warehouse, /report, /commission）；未授权路由重定向登录或 403。

### 7.2 关键页面

| 页面/模块     | 说明 |
|---------------|------|
| 登录          | 用户名+密码，可选记住登录；登录后写入 Token 与角色/权限 |
| 老板看板      | 销量趋势图、盈利概览、提成汇总；可下钻到业务员/时间 |
| 商家列表/详情 | 列表筛选（业务员、平台）；详情含订单、报价、采购摘要 |
| 订单列表/详情 | 多状态筛选、导入入口；详情含订单行、关联报价单/采购单/发货 |
| 报价单列表/编辑 | 新建（从订单选择）、编辑、发送、确认；预览与导出 |
| 采购单列表/执行 | 生成入口、进度维护、入库关联 |
| 发货与面单    | 待发货订单、生成发货单、面单打印、物流单号登记 |
| 提成管理      | 规则配置、提成记录列表、审核与调整 |
| 快递与物流    | 快递公司列表、国家运费维护、按公司/国家查询 |
| 订单文件转换  | 上传报价新 Excel + Tracking&Cost Excel，执行转换，下载三份结果 Excel |

### 7.3 权限控制

- 菜单：根据角色/权限动态生成，无权限的菜单不展示。
- 按钮：如“发送报价”“审核提成”等，无权限时隐藏或禁用。
- 接口：后端对所有写操作做权限与数据归属校验，防止越权。

## 八、扩展与集成预留

### 8.1 店小秘

- 预留“订单同步”接口：支持通过店小秘开放 API 或导出文件导入订单，映射平台订单号、金额、商品到本系统订单表。

### 8.2 1688

- 采购单中保存 1688 商品链接与规格；后续可扩展 1688 API 获取价格、库存或下单（若开放）。

### 8.3 快递与面单

- 面单格式与打印机对接（模板+数据接口）；预留快递公司、单号校验或电子面单 API 对接。

### 8.4 通知

- 报价单发送、付款到账、采购到货等可触发站内消息或邮件，配置项放在系统参数中。

## 九、部署与运维建议

- **环境**：开发、测试、生产分离；生产使用 HTTPS、独立数据库与 Redis。
- **备份**：数据库定期备份；关键操作日志与审计表定期归档。
- **监控**：接口耗时、错误率、登录失败率；可选 APM 与日志聚合。
- **发布**：前后端独立构建；后端 API 版本可放在路径前缀（如 /api/v1）便于兼容。
